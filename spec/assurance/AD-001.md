# tl-parse v0.1 Architecture Description

## System Boundary

The crate owns textual tokenization, parsing, source diagnostics, canonical
formatting, malformed/fuzz corpora, and thin CLI behavior. tl-syntax owns the
formula graph and semantic-profile identities. Callers own proposition-name
resolution, evaluation, rewriting, monitoring, and application I/O policy.

## Views

1. A bounded lexer recognizes only the checked-in ASCII dialect and records
   half-open byte spans.
2. A deterministic precedence parser builds topologically ordered tl-syntax
   nodes directly and retains recovery diagnostics on failure.
3. A bounded iterative formatter emits one fully parenthesized canonical form.
4. The library exposes versioned reports; a thin CLI delegates to the library.
5. Malformed fixtures and fuzz seeds exercise adversarial boundaries.
6. Evidence tooling packages exact source, dependencies, schemas, checks, and
   open human decisions under PGM-01.

## Decisions

tl-parse directly builds a topological graph rather than a second AST. A
closed ASCII dialect, fully explicit canonical output, stable diagnostic codes,
iterative formatting, and logical counters make ambiguity and resource outcomes
reviewable. tl-parse trusts the exact pinned tl-syntax constructors and structural
validator. It does not trust source text, files, stdin, corpus metadata, or
caller-supplied limits. Git, Rust, Quire, JSON Schema, and PGM validation are
identified evidence tools, not runtime dependencies.

The principal control flow is:

```text
source + profile + limits
  -> lexer tokens/diagnostics
  -> precedence parser -> tl-syntax validation -> document or no document
validated formula + format limits -> iterative canonical formatter -> text/error
library report -> optional CLI rendering
exact clean source -> retained PGM-01 candidate evidence -> human review
```

## Risks

Generated/fuzz evidence is bounded and the proposition syntax is intentionally
numeric-only in v0.1. Lexical, syntax, interval, profile, validation, source, token, node, depth,
diagnostic, work, output, I/O, and usage failures remain explicit. No partial
document or partial canonical output is labeled successful.
