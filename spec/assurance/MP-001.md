# tl-parse v0.1 Measurement Plan

## Decision Use

The evidence informs the human source-release decision. Passing measurements
do not themselves approve, certify, accredit, publish, or qualify a consumer.

## Metric and Rule

The metric is the proportion of applicable obligations with a current passing
outcome. The existing all-obligations-must-pass rule is represented by `>= 1.0`;
failed, missing, skipped, invalid, and non-conclusive outcomes stay individually
visible and cannot contribute to the numerator. An empty applicable population
is invalid, not a perfect proportion. The v2 definition adds the numeric rule
and binds the protected measurement apparatus; v1 observations must not be
rejudged under v2. The expected outcomes originate in human-authored
requirements and fixtures, with independent mechanical checks where declared.

The estimate counts current passing applicable obligations in the numerator
and all applicable obligations in the denominator. Failed, missing, skipped,
invalid, and non-conclusive outcomes remain separately reported. A candidate
passes the `{ comparator: ge, threshold: 1.0 }` rule only when every
applicable obligation passes. An empty applicable population has no finite
estimate and is refused.

## Population

The population is every TM-001 criterion, operator class, malformed/resource
fixture, fuzz seed, generated case, CLI path, public check, and schema gate in
the exact candidate revision.

## Decision Rule

The `proportion` estimate is the number of applicable obligations with a
current passing result divided by the number of applicable obligations. An
obligation that fails, has an invalid or skipped outcome, or lacks current
evidence counts in the denominator and not in the numerator. Invalid and
skipped outcomes are still reported separately, not only folded into the
proportion.

The rule `{ comparator: ge, threshold: 1.0 }` therefore holds only when every
applicable obligation passes on current evidence, and blocks the candidate
otherwise. An empty applicable population has no finite estimate and is
refused rather than passed.

## Collection Procedure

`make assurance-inputs` is the only step that runs a producer. It writes one
structured result per proof obligation under `target/assurance/`. Everything
downstream consumes those files and refuses to create them, so an absent input
is an error naming that target rather than a step the driver silently performs.

`scripts/assurance_chain.py` then reads each producer's own verdict out of the
bytes it wrote, seals a proof attestation stating that verdict, and hands the
bytes to Quoin for intake, which re-checks their digest and refuses a mismatch.
No verdict is inferred from an exit code alone or recovered from a transcript.

The Rust fuzz producer combines the launched process status with the artifact
directory and declared prerequisite state, then writes the resulting domain
outcome and normalized entry. The assurance chain reads those fields and retains
the exact JSON bytes; it does not parse libFuzzer console text. Structured
artifact identities are retained in this increment. Binary crash bytes remain
outside the retained population until `agent-ix/quoin#363` supplies the shared
attachment contract.

There is no local collector, envelope, manifest, anchor, or store. A failing
producer is retained the same way a passing one is — as the bytes it wrote,
under the attestation that states what those bytes say.

## Interpretation

Passing deterministic checks supports independent review of the exact
candidate. Generated and fuzz populations do not prove all possible inputs.
Human review and release state remain pending in candidate evidence.
